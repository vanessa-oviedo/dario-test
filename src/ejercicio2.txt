Suggestions: 

Keep the current status denormalized on Order
Store CurrentStatusId, CurrentStatusDate, CurrentStatusChangedBy on dbo.[Order] so reads don’t scan a large history. Maintain the history separately in OrderStatusHistory.

Enforce the Picked Up date rule with a CHECK constraint
Only “Picked Up” must have a date. Use
CK_Order_PickedUpDate: (CurrentStatusId IS NULL OR CurrentStatusId <> 3 OR CurrentStatusDate IS NOT NULL)
and the analogous constraint on OrderStatusHistory.

Use a pointer to the current quote on Order
Save CurrentOrderBuyerQuoteId (with a composite FK to OrderBuyerQuote(OrderBuyerQuoteId, OrderId)) so you can fetch the chosen quote with a single join—no “IsCurrent” scans.

Don’t put quote on Buyer; put it per ZIP and per order

Baseline per ZIP: BuyerZipCoverage.DefaultQuoteAmount (Buyer×ZIP).

Actual per order: OrderBuyerQuote.Amount.
This matches “for each ZIP, buyers and a quote” and lets a buyer bid differently per ZIP and per order.

Avoid IsCurrent in history tables
History should be append-only; the “current” is defined by the pointer on Order. This keeps writes simple and reads fast.

EF query style: project only what you need
Use AsNoTracking(), conditional filters, and projection to a DTO so you don’t pull unnecessary columns/entities. Handle dateTo inclusively by making it < dateTo + 1 day.

Batch balance updates from invoices (no N+1)
Save invoices, group by CustomerId, load only affected customers, update balances in memory, and call one SaveChanges. Optionally use EF Core 8 ExecuteUpdateAsync to do it in SQL. Wrap in a transaction.

Consider denormalizing hot read fields on Order
Snapshot CarYear/Make/Model/Submodel, CurrentBuyerId/Name, CurrentQuoteAmount, and CurrentStatusName. That turns the top summary query into a single-table select. Keep them in sync in application logic when the car/quote/status changes.

Add indexes to speed up common reads

IX_Order_CurrentPointers on (CurrentOrderBuyerQuoteId, OrderId) INCLUDE (CurrentStatusId, CurrentStatusDate)

UX_OrderBuyerQuote_Id_OrderId on (OrderBuyerQuoteId, OrderId) (unique)

IX_BuyerZipCoverage_Zip on (ZipCode) INCLUDE (BuyerId, DefaultQuoteAmount, BuyerZipCoverageId)

IX_Car_SubmodelId, IX_CarSubmodel_ModelId, IX_CarModel_MakeId to cover the vehicle join chain

IX_OrderBuyerQuote_Order_AmountDesc on (OrderId, Amount DESC) INCLUDE (OrderBuyerQuoteId, BuyerZipCoverageId)

IX_Order_CurrentStatusId INCLUDE (CurrentStatusDate) for dashboards/filters

IX_Order_CustomerId INCLUDE (CreatedAt, ZipCode) for customer views

IX_Invoice_CustomerId_IssuedAt, IX_Invoice_OrderId, and a filtered IX_Invoice_Open (WHERE IsPaid=0) for billing

Make CurrentStatusDate nullable by design
It’s required only for “Picked Up”. Keeping it nullable prevents fake timestamps for other statuses; the CHECK enforces the business rule.

Use LEFT JOINs for the summary read
Orders might not yet have a current quote or status; LEFT JOIN avoids dropping those rows.

Optional: compiled queries for EF hot paths
For very high-traffic endpoints with stable shapes, EF Core compiled queries can reduce overhead.

Optional: add IsActive to Order if you’ll filter by it
If your API uses bool? isActive, a BIT IsActive on Order plus an index ((IsActive)) keeps those filters cheap.

Keep status updates atomic (app-side)
When changing the current status, update Order.Current* and insert into OrderStatusHistory in the same transaction so snapshots and history never drift.

Validate domain data at the DB layer, too

Monetary fields > 0 (CHECKs already present)

Car year in allowed range (CHECK already present)

Uniqueness (UQ_Buyer_Zip, UNIQUE names) to prevent duplicates across catalogs

Cache “mostly static” catalogs
For OrderStatus, CarMake/Model/Submodel, ZipCode, use cache-aside; with multiple app instances, prefer distributed cache (e.g., Redis) and versioned keys or pub/sub invalidation.
